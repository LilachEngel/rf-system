# Real-Time RF Data Pipeline & Monitoring System

מערכת בזק מבוזרת לעיבוד, ניטור ואגירת נתוני רדיו (RF) בזק אמת. המערכת קולטת חבילות מידע, מבצעת עיבוד נתונים, מזהה חריגות, ושומרת את המידע במסדי נתונים מרובים בהתאם לסוג המידע.

---

## 🏗️ ארכיטקטורת המערכת (Architecture)
הארכיטקטורה מורכבת מהרכיבים הבאים:
1. **Producer (`producer.py`)**: מייצר סימולטיבית חבילות נתוני RF רדיו-טכניים ודוחף אותם לתור הודעות.
2. **Message Broker (Redis)**: משמש כתור הודעות מהיר (`rf_queue`) להעברת הנתונים בין היצרן לצרכן.
3. **Consumer (`consumer.py`)**: שולף את הנתונים מהתור, מחשב ממוצע נע, מזהה חריגות עוצמה, שומר את הנתונים הגולמיים ל-MinIO, את המטא-דאטה ל-PostgreSQL, ואת ההתראות ל-MongoDB.
4. **API Backend (`api.py`)**: שרת FastAPI המספק נקודות קצה (Endpoints) לשליפת הדגימות וההתראות עבור ממשק המשתמש.
5. **Frontend (React + Vite)**: ממשק מששמש גרפי (דשבורד) המציג את נתוני המערכת וההתראות בזמן אמת.

---

## ⚙️ הצדקת בחירת מנגנון המקביליות (Concurrency Choice)
עבור רכיב ה-**Consumer**, בחרנו לעבוד במודל של **Single-Threaded Blocking Loop בשילוב תור מנוהל (Redis Blocking Pop - `blpop`)**:
* **סיבה מרכזית:** הצרכן מעבד את ההודעות מהתור בצורה טורית ומובנית (FIFO), כאשר כל הודעה עוברת סדרת פעולות עוקבות מול מסדי הנתונים (Redis ➡️ MongoDB ➡️ MinIO ➡️ PostgreSQL). 
* **תקשורת I/O Bound:** עיקר הזמן של הצרכן אינו מבוסס על חישובים מתמטיים כבדים (CPU-bound) שדורשים Multiprocessing, אלא על המתנה לתשובות מרשת האינטרנט ומסדי הנתונים (I/O operations). שימוש ב-`blpop` חוסך צריכת משאבים מיותרת ומבטיח סנכרון מלא ואמינות גבוהה מבלי לאבד הודעות בדרך.
